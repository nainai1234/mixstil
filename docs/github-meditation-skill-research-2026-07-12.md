# GitHub 冥想 Skill / 程序调研

日期：2026-07-12  
目的：寻找可复用的冥想内容生成、脚本编排、TTS 韵律和音频后期项目。调研不等于授权，不直接把陌生仓库接入产品。

## 1. 结论先行

没有找到一个同时满足“成熟、活跃、可商用、内容结构可靠、支持中文和英文、可以直接生成专业冥想作品”的 GitHub 冥想 Skill。

GitHub 搜索中的冥想生成项目大多是个人 Demo：

- `UrmiKarmakar/Calm-AI-Meditation-App-Backend-Django`：1 star，无明确仓库许可证。
- `UzayPoyrza/guided-meditation-generator`：0 star，ElevenLabs 批量生成 Demo，无明确仓库许可证。
- `salmansoltaniyan/Meditation-Generator`：0 star，Google TTS + 背景音乐循环 Demo，无明确仓库许可证。
- `rjrahul24/moodscape-guided-meditations`：0 star，组合多个新模型的实验项目，不能因为描述写了 production-grade 就当成生产验证。
- “meditation skill” 精确搜索结果主要是 Alexa 示例或个人 Claude/语音 Skill，不能作为音频内容生产系统。

这些项目可以参考流程，但没有一个可以证明生成的内容符合专业冥想行业质量，也没有一个可以替代内容审核、授权和用户验证。

## 2. 值得复用的成熟组件层

### TTS / 韵律

- OpenVoice V2：MIT，适合自有授权音色的本地 Spike；不能把他人参考音色当作可用资产。
- CosyVoice：Apache-2.0 代码，中文和跨语言能力强；模型权重、音色和下载来源仍需逐项核对。
- Kokoro：Apache-2.0，适合英文轻量本地对照；中文需要单独验证。
- StyleTTS2、Chatterbox、Higgs Audio：可作为韵律/情绪研究，但模型权重、依赖和许可证必须重新核对。
- Whisper/FunASR：只能用于转写、漏字和发音 QA，不能解决 TTS 韵律。

### 音频后期

- FFmpeg：可用于裁剪、拼接、淡入淡出、响度和格式转换；必须避免用过重 EQ 或变调破坏人声。
- `pyloudnorm`、`librosa`、`pedalboard`：适合响度、峰值、瞬态、频谱和自动 QA。
- 这些组件解决工程问题，不会自动产生“疗愈感”。脚本分段、停顿和内容导演仍需独立设计。

## 3. 对当前音色异常问题的判断

用户听到“声音奇怪”时，不能先假设是 TTS 模型问题。应按以下顺序排查：

1. 原始 Edge-TTS 文件是否自然。
2. 分句拼接是否使用了有损 MP3 反复转码。
3. 是否叠加了 pitch、highpass、lowpass 或过度 loudnorm。
4. 句间静音是否真的为静音，而不是编码边界噪声。
5. 单声道、采样率和播放端是否造成异常。
6. 最后才比较不同 TTS 模型的音色和韵律。

当前产品应遵守：

- 默认不改 pitch。
- 默认不使用宽范围 EQ。
- 人声只做一次最终响度处理。
- 分句最好先转 PCM/WAV，再拼接和一次性编码，避免 MP3 片段反复有损拼接。
- 每个供应商保留“原始输出”和“最终母版”两份文件。

## 4. 不直接采用 GitHub 冥想 Demo 的原因

- 星标、提交活跃度和问题响应不足以证明音频质量。
- 很多仓库没有明确许可证，不能用于商用产品。
- “AI meditation”通常只是 LLM 写文本 + TTS + 循环音乐，没有阶段、留白、背景 Ducking 和长时间疲劳控制。
- 频率、脑波、Reiki 等营销标签不等于疗效证据。
- 参考音频、模型权重、第三方音乐和输出权利经常被混在一起，无法直接审计。

## 5. 对 DeepNill 的正确复用方式

只复用基础设施，不复制未经验证的内容：

```text
受控脚本和阶段 Recipe
-> TTS Adapter（可替换供应商）
-> PCM 级分句和停顿拼接
-> 轻量响度处理
-> 句子时间码和人声退出
-> 背景 Ducking
-> 技术 QA + 内容审核 + 授权审核
```

GitHub 项目只能进入后台实验目录，不能直接成为前台实时生成器，也不能绕过 `qa_status`、商用权和二创权检查。

## 6. 下一步执行

1. 先用原始 Edge-TTS 与“无后期处理”的 Edge-TTS 做对照，确认异常是否来自后期链。
2. 把分句拼接从 MP3 片段改为 PCM/WAV 中间格式，再一次性输出 MP3。
3. 对同一组 3 个冥想脚本做 OpenVoice、CosyVoice、Kokoro 或商业 API 的 A/B，保持文本、停顿、响度和背景完全相同。
4. 只比较自然度、重音、句末语气、呼吸感和长时间疲劳，不把模型宣传词当成结论。
5. 由内容审核和授权审核共同决定是否进入生产。

## 7. 最终判断

当前最成熟的方案不是“找到一个神奇的冥想 Skill”，而是：

- 继续使用我们自己的 Recipe V2 和脚本导演层。
- 采用成熟的 TTS/音频基础组件作为可替换 Provider。
- 把错误优先定位到后期处理和编排链。
- 通过专业内容审核和真实用户数据证明质量。
