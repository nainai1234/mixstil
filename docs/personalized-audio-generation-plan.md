# 个性化冥想与助眠音频生成方案

> 状态：V1.0 历史方案。2026-07-11 完成竞品复核后，执行基线已更新为 [V2.0 竞品调研与实施方案](./personalized-audio-generation-plan-v2.md)。V1 保留用于追踪决策变化，不再作为当前执行依据。

版本：V1.0  
日期：2026-07-11  
适用项目：SNOOZE / sleep-audio

## 1. 方案结论

产品应建设为一个“需求理解 + 音频配方 + 混合生产 + 自动混音 + 对话修改”的个性化音频创作工具，而不是一个从零生成完整歌曲的通用 AI 音乐产品。

首版采用混合生产策略：

1. 优先使用平台已审核的真实录音和内部生成素材。
2. 使用本地算法生成噪音、简单 Drone、节拍和可控声学层。
3. 使用本地或自建模型生成适合批量复用的音乐候选。
4. 只对内部能力无法满足的特殊音乐、音效和高质量多语种人声调用商用 API。
5. 所有声音最终进入统一的授权、技术 QA、听感 QA 和配方系统。

目标不是承诺固定的“本地完成 90%”，而是通过数据逐步达到：

- 常见请求的内部素材命中率不低于 80%。
- 外部 API 成本只发生在用户明确需要且内部资产不足的环节。
- 默认生成结果无需专业编辑即可试听、保存和分享。
- 用户可以只修改一个层次，不必整首重新生成。

## 2. 产品边界

### 2.1 首版解决的问题

用户通过自然语言描述自己的使用场景，例如：

> 我今天压力很大，想做一段 20 分钟的睡前放松音频。希望有轻柔雨声和温暖的氛围音乐，前 5 分钟加入中文女性引导，之后逐渐减少说话。

系统完成：

1. 提取目标、时长、语言、人声、环境、音乐、强度和禁用项。
2. 生成分段时间轴和多轨配方。
3. 优先从内部素材库匹配可用 Stem。
4. 必要时生成缺失的人声、音乐或特殊音效。
5. 完成自动混音、预览、质量检查和导出。
6. 支持继续修改，例如“雨声小一点”“去掉钢琴”“人声更慢”。

### 2.2 首版不解决的问题

- 不做任意风格的完整歌曲生成。
- 不承诺治疗失眠、焦虑或其他疾病。
- 不根据未经验证的 `432Hz`、脑波等标签宣传疗效。
- 不允许未完成授权审核的素材进入公开或商业导出。
- 不允许模型自动生成后未经检查就进入公共素材库。
- 不在首版开放任意用户上传素材参与公共作品生产。

## 3. 首发场景

首版使用五个可被用户理解和检索的场景，不以抽象视觉概念作为一级主题。

| 场景 | 用户目标 | 建议时长 | 默认结构 | 人声策略 |
| --- | --- | ---: | --- | --- |
| 深层睡眠 | 降低刺激、稳定遮蔽环境声 | 30/60/120 分钟 | 噪音 + 自然声 + 极弱 Pad | 默认无，或仅开头 5 分钟 |
| 夜醒回睡 | 夜间醒来后减少认知刺激 | 15/30 分钟 | 棕噪音 + 稳定雨声 + 无明显旋律 | 短句、低密度、长停顿 |
| 冥想呼吸 | 跟随节奏进行呼吸或身体觉察 | 5/10/20 分钟 | 环境层 + Pad + 低频点缀 | 分阶段引导，结尾减少说话 |
| 情绪放松 | 工作后或压力状态下短时安放 | 10/20/30 分钟 | 自然声 + 温暖音乐 + 柔和转场 | 可选完整引导 |
| 专注工作 | 遮蔽干扰并维持稳定注意 | 25/50/90 分钟 | 粉噪音/流水 + 无歌词音乐 | 默认无人声 |

“失重放松”可以作为情绪标签或视觉包装，但不作为首版一级业务场景。

## 4. 首发内容资产包

### 4.1 数量和组成

首发目标为 24–30 个经过审核的核心 Stem，而不是继续追求文件总量。

| 类别 | 目标数量 | 首发重点 |
| --- | ---: | --- |
| Nature | 8–10 | 轻雨、长雨、海浪、河流、森林、水流、微风、火焰 |
| Noise | 4–5 | 柔和白噪、粉噪、深/柔棕噪、风扇或空调 |
| Music | 6–8 | 温暖 Pad、低频 Drone、稀疏钢琴、音钵、无节奏氛围层 |
| Accent | 4–5 | 柔和钟声、音钵、水滴、远雷、转场音 |
| Voice | 4–6 | 中英文呼吸、睡前放松、夜醒回睡候选 |

每个首发 Stem 必须至少服务两个场景；只适用于单一小众请求的素材不进入核心包。

### 4.2 当前资产基线

当前仓库已经具备：

- 约 124 个本地音频文件。
- 15 个内部生成噪音 Stem。
- 多批自然声和点缀音候选。
- 19 个音乐候选。
- 10 个中英文人声候选。
- 数据库 Seed 当前约登记 83 个 Stem。

执行前必须处理两个已知问题：

1. `public/audio/nature/batch-04` 中的 30 个文件尚未接入数据库 Seed。
2. 部分音乐说明仍要求 Content ID 与人工听感审核，但当前 Seed 默认值可能把它们标为 `approved`。

因此第一阶段是资产盘点和治理，不是立即采购或重新生成全部素材。

### 4.3 单个素材入库标准

每个 Stem 必须具备：

- 唯一 ID 和不可变文件 Hash。
- 来源平台、作者、原始链接和获得日期。
- 商业使用、二次创作、署名、原始文件再分发权限。
- 采样率、声道、位深/码率、真实时长。
- 峰值、综合响度、静音、削波、直流偏移检测结果。
- 循环接缝检测和人工重复疲劳检查。
- 场景、情绪、频谱、强度和推荐音量标签。
- 人工审核人、审核时间和审核备注。

只有 `qa_status = approved` 且允许商业二创的素材可以用于渲染导出。

## 5. 音频配方模型

### 5.1 用户需求结构

自然语言首先转换为结构化 `AudioIntent`：

```json
{
  "goal": "sleep",
  "durationSeconds": 1200,
  "language": "zh-CN",
  "guidance": {
    "enabled": true,
    "voiceStyle": "warm_female",
    "density": "low",
    "endAtSeconds": 300
  },
  "environment": ["gentle_rain"],
  "music": {
    "enabled": true,
    "style": ["warm_pad"],
    "melodyLevel": "minimal"
  },
  "intensity": "soft",
  "avoid": ["thunder", "birds", "piano"],
  "userText": "..."
}
```

意图解析必须保留用户明确表达，不能用模型猜测医疗状况或敏感个人属性。

### 5.2 配方时间轴

配方由阶段和轨道组成：

```text
Arrival      0:00–2:00   建立环境，低音量进入
Guidance     2:00–5:00   人声引导，背景自动压低
Settling     5:00–10:00  人声退出，音乐和自然声稳定
Sustain     10:00–18:00 保持低变化，点缀音极少出现
Exit        18:00–20:00 柔和淡出或保持长循环
```

每条轨道至少记录：

- `stemId`
- `role`: base / environment / music / accent / voice
- `startTime`、`duration`、`trimStart`、`trimEnd`
- `gainDb` 或可映射到增益的音量值
- 淡入、淡出和循环策略
- Ducking 规则
- 点缀音的确定性触发时间
- 来源类型：library / local_generated / external_generated / user_recorded

点缀音不能只在客户端临时随机触发。系统应使用随机种子生成固定事件，并把事件写入配方，确保预览与导出一致。

### 5.3 兼容性规则

首版先用人工策划规则保证质量下限：

- 每个主题定义允许、推荐、禁止的 Stem。
- 每个 Stem 定义推荐音量范围和适用角色。
- 两个音乐层同时出现时检查调性和频谱冲突。
- 鸟叫、雷声和高频虫鸣默认不用于夜醒回睡。
- 人声期间背景层自动降低 4–8 dB。
- 睡眠场景限制突然瞬态和高密度点缀音。
- 专注场景禁止随机人声和明显旋律高潮。

## 6. 混合生成架构

### 6.1 能力路由

```text
用户请求
  -> 意图解析
  -> 生成候选配方
  -> 查询已审核素材
  -> 查询本地可合成能力
  -> 判断缺口和质量要求
  -> 必要时调用外部服务
  -> 统一入临时资产区
  -> 技术 QA + 安全/授权检查
  -> 编排与渲染
```

路由优先级：

1. 已审核内部素材：延迟最低、成本最低、质量稳定。
2. 本地确定性合成：白/粉/棕噪音、简单节拍、基础 Drone。
3. 已审核的本地模型生成资产：适合可复用 Pad 和氛围层。
4. 外部生成 API：特殊音效、高质量 TTS、内部无法满足的音乐。
5. 无可靠结果时回退到相近素材，并明确告知用户，而不是生成不可用文件。

### 6.2 本地模型验证门槛

Stable Audio Open 或其他本地模型在进入架构前必须通过技术 Spike：

- 当前 Mac 是否原生支持，是否依赖 CUDA。
- 峰值内存和单条生成耗时。
- 可稳定生成的时长与采样率。
- 20 次生成的成功率和可用率。
- Prompt 对无节奏、长 Attack/Release 的遵从程度。
- 商用授权、模型权重许可和输出权利。
- 后处理后是否可形成无明显接缝的循环。

未通过验证前，不把它计入上线能力或成本模型。

### 6.3 外部 API 适用边界

外部 API 不与具体供应商永久绑定，统一通过 Provider Adapter 接入。

| 能力 | 首选路径 | 外部 API 使用条件 |
| --- | --- | --- |
| 自然环境声 | 授权实地录音 | 罕见或虚构环境且内部无素材 |
| 噪音 | 本地确定性合成 | 原则上不调用 |
| Pad/Drone | 内部素材或本地生成 | 特殊风格且付费等级允许 |
| 点缀音 | 已审核素材 | 特殊单次音效缺失 |
| 引导人声 | 已审核 TTS/内部生产 | 语言、音色或质量内部不满足 |
| 文案 | 模板 + LLM | 个性化引导并通过安全检查 |

每次外部调用记录供应商、模型、版本、成本、延迟、授权快照、Prompt Hash 和输出 Hash。

## 7. 人声引导方案

人声不是一个 TTS 按钮，而是一条独立生产链：

1. 根据场景和时长选择脚本骨架。
2. 生成或改写个性化文案。
3. 执行医疗化表达、安全和长度检查。
4. 用户在生成语音前可编辑文本。
5. 按语言、音色、语速、停顿生成 TTS。
6. 检查发音、漏读、异常音和响度。
7. 将句子级时间码写入配方。
8. 混音时执行背景 Ducking。

首版只支持中文和英文，每种语言先保留 2–3 个经过审核的音色。不要一开始开放无限音色选择。

脚本必须避免：

- 保证入睡或保证改善。
- 治疗焦虑、失眠、创伤等医疗表达。
- 危险呼吸保持时长。
- 对用户心理状态作未经确认的判断。

## 9. API 规划

### 9.1 用户生成

- `POST /api/generation/intent`：解析并返回可编辑需求。
- `POST /api/generation/recipes`：生成候选配方和缺口说明。
- `POST /api/generation/jobs`：启动缺失资产生成。
- `GET /api/generation/jobs/:id`：查询进度和费用状态。
- `POST /api/generation/recipes/:id/revise`：执行局部对话修改。
- `POST /api/mixes/:id/render`：沿用现有最终渲染接口。

### 9.2 内容运营

- `GET /api/admin/assets/qa-queue`
- `POST /api/admin/assets/:id/approve`
- `POST /api/admin/assets/:id/reject`
- `GET /api/admin/themes`
- `POST /api/admin/templates`
- `POST /api/admin/compatibility`

所有生成接口必须支持幂等键，避免重试造成重复计费。

## 10. 音频质量标准

上线前确定一份实际测量基线，首版建议：

- 导出格式：AAC/MP3 供分享，保留 WAV 母版。
- 统一采样率：48 kHz 或 44.1 kHz，项目内只能选一种主标准。
- 禁止削波；True Peak 目标不高于约 -1 dBTP。
- 整体响度按内容类型制定范围，不强行把睡眠音频做得像流行音乐一样响。
- 检测首尾接缝、短循环重复感、突然瞬态和异常静音。
- 人声清晰但不贴脸，背景 Ducking 不产生明显抽吸感。
- 10 分钟以上作品至少进行一次完整人工试听抽检。

`432Hz`、Alpha、Theta 或 binaural 等标签只有在可测量、可复现时才能写入技术元数据；不能自动转化为疗效宣传。

## 11. 成本与降级策略

每次生成在执行前估算成本：

```text
预计成本 = LLM 文案 + TTS 字符/时长 + 音乐生成时长 + 音效调用 + 存储 + 渲染
```

首版策略：

- 免费用户只能使用已审核素材和有限 TTS。
- Pro 用户可以触发更长人声、特殊音色和有限外部音乐生成。
- 同一 Prompt 和参数的可复用生成资产可以缓存，但必须遵守供应商条款。
- API 超时或预算超限时回退到内部素材配方。
- 外部生成失败不能阻塞用户保存已有草稿。
- 设置用户级、日级和供应商级成本上限。

## 12. 执行计划

### Phase 0：基线冻结与治理，3–5 个工作日

任务：

- 导出所有本地文件和数据库 Stem 清单。
- 对齐文件、Seed 和数据库记录，找出孤儿文件与缺失文件。
- 接入或明确排除 `batch-04`。
- 将未完成 Content ID/听感审核的音乐改为 `needs_review`。
- 建立首发 QA 表格和审核责任人。
- 确定产品正式名称和统一 ID 命名规范。

验收：

- 资产数量可解释，文件与记录一一对应。
- 没有待审核音乐被当作已批准素材导出。
- 所有批准素材具备 Hash、来源和授权记录。

### Phase 1：首发核心素材包，5–8 个工作日

任务：

- 从现有素材筛选 24–30 个核心 Stem。
- 完成技术检测和人工听感 QA。
- 补充场景、频谱、强度、音量和循环标签。
- 为五个首发场景各制作 3 个标准作品。
- 记录素材兼容与冲突关系。

验收：

- 至少 15 个标准作品能完整渲染和下载。
- 每个场景至少 3 个作品且听感明显不同。
- 不出现明显爆音、接缝、突兀高频或授权阻断。

### Phase 2：配方引擎 V2，5–8 个工作日

任务：

- 定义 `AudioIntent` 和 Recipe V2 Schema。
- 把五个场景规则数据化。
- 支持时长、环境、音乐、人声、强度和排除项。
- 建立候选打分、兼容性检查和确定性点缀事件。
- 保留现有规则分类作为降级路径。

验收：

- 30 条标准测试 Prompt 的关键字段提取准确率不低于 90%。
- 相同请求和随机种子产生相同配方。
- 禁用项不会出现在最终轨道中。

### Phase 3：真实人声链路，7–10 个工作日

任务：

- 建立中英文脚本模板。
- 接入脚本生成、编辑、安全检查和真实 TTS。
- 保存句子级时间码和 Provider 元数据。
- 实现背景 Ducking 和发音 QA 流程。
- 替换当前界面中的占位生成按钮。

验收：

- 中英文各至少 2 个批准音色。
- 三类人声场景可完整生成、预览和导出。
- 人声失败时能够回退到无人声版本。

### Phase 4：本地音乐生成 Spike，3–5 个工作日

任务：

- 选择最多两个候选模型，不同时铺开多个方案。
- 对 6 个 Pad/Drone Prompt 各生成 5 个变体。
- 记录耗时、内存、成功率、可用率和许可结论。
- 使用统一脚本完成裁切、淡化、循环和技术检测。

继续条件：

- 30 个候选中至少 30% 经人工审核可用。
- 单条成本和等待时间符合产品体验。
- 许可允许目标商业场景。

不满足继续条件时，保留采购/委托制作路线，不让本地模型阻塞上线。

### Phase 5：能力路由与外部 Provider，5–8 个工作日

任务：

- 建立 Provider Adapter 和 `generation_jobs`。
- 实现内部命中、缺口识别、预算判断、外部调用和回退。
- 接入最多一个 TTS Provider 和一个音效/音乐 Provider。
- 增加超时、重试、幂等、成本和审计记录。

验收：

- 常见标准请求内部素材命中率不低于 80%。
- 外部失败不会丢失作品或产生重复计费。
- 每个生成文件都能追溯到模型、Prompt、许可和费用。

### Phase 6：对话式修改，5–7 个工作日

首版支持以下确定性修改：

- 增大/减小某一层音量。
- 增加、替换或删除一个环境声。
- 去掉音乐或人声。
- 调整人声语速、音色和结束时间。
- 延长总时长。
- 降低点缀音频率。

验收：

- 局部修改不会无故改变其他轨道。
- 修改前后都有版本记录并可撤销。
- 只重新生成真正受影响的资产。

### Phase 7：小流量上线与数据验证，2 周观察期

观察指标：

- Prompt 到可预览结果成功率。
- 首次预览等待时间 P50/P95。
- 用户生成后继续编辑的比例。
- 保存、导出和分享转化率。
- 内部素材命中率与外部 API 使用率。
- 单个成功作品的平均外部成本。
- 人工 QA 退回率和用户举报率。
- 同一作品的复听和完播情况。

首版发布门槛：

- 生成成功率不低于 95%。
- 内部素材请求 P95 在 10 秒内得到可编辑配方。
- 渲染失败有明确原因并可恢复。
- 公开作品全部通过授权门槛。
- 不以生成数量代替真实试听质量。

## 13. 工作优先级

### P0：上线前必须完成

- 资产盘点、授权和 QA 状态修复。
- 首发核心素材包。
- 五场景模板和 Recipe V2。
- 真实 TTS 链路。
- 授权门槛、渲染和失败回退。
- 生成成本和 Provider 审计。

### P1：首版上线后尽快完成

- 本地 Pad/Drone 生成。
- 对话式局部修改。
- 更完整的兼容性评分。
- 自动响度、接缝和瞬态报告。

### P2：数据证明需求后再做

- 更多语言和音色。
- 用户声音克隆。
- 任意用户上传进入公共素材库。
- 大规模音乐模型集群。
- 医疗或生理反馈相关能力。

## 14. 责任边界

建议继续保持两层系统：

- Liaoyu / Content OS：负责批量内容规划、脚本、TTS、音乐/自然声生产、母带 QA、版权和发布审核。
- sleep-audio：负责用户描述、简化配方生成、试听修改、作品保存、渲染、分享和数据反馈。

生产系统只把审核通过的资产发布给用户端；用户端产生的临时生成资产不能自动晋升为公共素材。

## 15. 第一轮立即执行清单

第一轮只推进 Phase 0 和 Phase 1：

1. 修正音乐候选的默认 QA 状态。
2. 决定 `batch-04` 中哪些文件入库，补齐 Seed。
3. 生成完整资产审计清单。
4. 按五个场景选出 24–30 个核心 Stem。
5. 定义五个场景各 3 个标准配方。
6. 完成 15 个作品的渲染和整段试听。
7. 输出缺口清单，缺什么才生成或采购什么。

第一轮结束后再决定本地模型和外部 API，避免在现有资产尚未治理时重复花费。
